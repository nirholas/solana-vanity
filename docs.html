Quick start

Grind in the browser at the grinder: nothing to install, and the key never leaves the tab.

Locally, with Node 20 or newer:

git clone https://github.com/nirholas/solana-vanity
cd solana-vanity
npm install
npm run dev          # site on :5180, API on :8787

Or grind from the command line without cloning anything:

npx solana-vanity grind --prefix AGNT --suffix pump
npx solana-vanity quote --prefix AGNT
npx solana-vanity appraise <address>

The difficulty model

Almost every vanity tool models an n-character Solana pattern as 58n expected attempts. That is correct for trailing characters and wrong for the leading one, because Base58 is a positional encoding of a 256-bit integer, not a string of independent symbols.

A Solana public key is 32 bytes, so once leading zero bytes are stripped it spans [2248, 2256). Base58 renders such a value in 44 digits when it is at least 5843 and 43 digits otherwise, and those two thresholds carve the alphabet into six bands: 

'1'      P = 3.906e-3   a leading zero byte, exactly 1/256
'2'-'3'  P = 5.804e-2   44-digit encodings only
'4'      P = 5.814e-2   plus the sliver of 43-digit that clears 2^248
'5'-'H'  P = 5.904e-2   3.43x easier than the uniform model claims
'J'      P = 1.433e-2   where the 44-digit range runs out
'K'-'z'  P = 1.001e-3   17.2x harder than claimed - 40 of the 58 symbols

src/base58-distribution.js counts this exactly with BigInt interval arithmetic over the whole key space: it is not a fitted table or an approximation. The consequence is practical: a pattern starting with K is seventeen times more expensive than a naive quote says, and one starting with 5 is three times cheaper. The rarity page renders the full table live.

Suffixes really are uniform at 58-n: the low-order digits of a uniform 256-bit integer are equidistributed to within about 10-53 at the six-character ceiling, far below double precision.

Proof-of-grind certificates

A certificate is a signed statement about a ground address, in a format anyone can verify offline. It carries the pattern, the difficulty under a named model, a rarity breakdown, a freshness nonce, and, for split-key grinds, a non-custody assertion. It is signed with the service's long-lived Ed25519 key, published at /.well-known/solana-vanity.json.

Verification recomputes every claim rather than trusting the document:

import { verifyProofOfGrind } from 'solana-vanity/proof-of-grind';

const keyring = (await (await fetch(BASE + '/.well-known/solana-vanity.json')).json()).attestationKeys;
const result  = verifyProofOfGrind(certificate, { keyring });

result.valid;                   // true / false
result.checks;                  // per-check audit with human-readable detail

The freshness nonce exists so the same address cannot be sold twice as "freshly ground": a verifier holding the canonical first certificate for an address detects a duplicate. The verify page runs this code in your browser.

What a certificate cannot prove: that whoever ran the grinder did not keep a copy of the key. Only grinding it yourself, or split-key delegation, proves that. The certificate says so explicitly by naming the grind format.

Split-key delegation

Hard patterns need more compute than one browser tab has, and handing the job to a remote grinder normally means handing over the key. Split-key grinding removes that trade with group arithmetic on Ed25519, basepoint B, scalar order L:

  1. The requester picks a secret scalar a1 locally and publishes only P1 = a1·B.
  2. A worker searches offsets a2, testing A = P1 + a2·B against the pattern. It knows a2 and P1 but not a1, so it cannot compute the final secret.
  3. On a hit the worker returns (a2, A). Anyone can check P1 + a2·B == A with no secret.
  4. The requester combines aFinal = (a1 + a2) mod L on their own machine. Because aFinal·B = P1 + a2·B = A, that scalar controls exactly the vanity address, and it only ever exists there.

The offset is not a secret (it is useless without a1), so it can travel in the clear, and the certificate can publish a2·B as a checkable non-custody proof.

The honest catch: aFinal is a raw Ed25519 scalar, not a 32-byte seed. You cannot invert SHA-512 to find a seed that expands to a chosen scalar, so a split-key wallet is an expanded key: it signs perfectly and is a valid Solana account, but seed-only wallet imports will reject it. Use it with an SDK signer, or grind a seed-based key yourself when import matters.

HTTP API

Machine-readable schema: /openapi.json. Agent card: /.well-known/agents.json.

EndpointWhat it does
POST /api/quoteExact probability, expected attempts, rarity tier and ETA for a pattern. Also returns the naive 58n figure and the ratio, so you can see the correction.
POST /api/appraiseRarity of an address that already exists.
GET /api/difficulty/leading-charactersThe exact Base58 leading-character table.
POST /api/certifySign a proof-of-grind certificate. Refuses to attest an address that does not match the claimed pattern.
POST /api/verifyVerify a certificate against the published key ring.
POST /api/splitkey/grindDelegated grinding. Send p1 and a pattern; get an offset back.
POST /api/splitkey/verifyCheck that an offset really produces a claimed address.
POST /api/grindCustodial server-side grind. Disabled unless the operator sets ALLOW_SERVER_GRIND=1.
 
curl -s https://solana-vanity.dev/api/quote \
  -H 'content-type: application/json' \
  -d '{"prefix":"AGNT","attemptsPerSecond":120000}'

CLI

npx solana-vanity grind --prefix AGNT --suffix pump --out wallet.json
npx solana-vanity grind --prefix AGNT --mnemonic       # a seed phrase, not a raw key
npx solana-vanity delegate --prefix AGNT --api https://solana-vanity.dev
npx solana-vanity quote --prefix AGNT --rate 120000
npx solana-vanity appraise 5CyxU...  --suffix-len 4
npx solana-vanity verify certificate.json

grind uses the same WebAssembly module as the site, across every core the machine reports. delegate runs the split-key protocol against a remote API and combines locally, so the remote side never sees a secret, which makes it safe to point at a service you do not control.

MCP server

Six tools over the Model Context Protocol, so an assistant can quote, appraise, grind, delegate and verify:

{
  "mcpServers": {
    "solana-vanity": { "command": "npx", "args": ["-y", "solana-vanity", "mcp"] }
  }
}
vanity_quoteDifficulty, rarity and ETA for a pattern.
vanity_appraiseRarity of an existing address.
vanity_grindGrind locally on the machine running the server.
vanity_split_key_grindDelegate to a remote API without exposing a key.
vanity_verify_certificateVerify a certificate offline.
vanity_leading_charactersThe exact Base58 probability table.

Self-hosting

One Fetch handler, two hosts. On Node:

npm run build
ATTESTATION_SEED=$(node server/keygen.mjs | head -1 | cut -d= -f2) npm start

On Cloudflare Workers, with the built site served from the assets binding:

npm run build
npx wrangler secret put ATTESTATION_SEED
npx wrangler deploy

/api/grind is the one endpoint that behaves differently on the edge: it needs the WebAssembly grinder loaded from disk, so a Worker answers 501 and points at /api/splitkey/grind, which is pure arithmetic and runs anywhere.

VariableMeaning
ATTESTATION_SEED32-byte Ed25519 seed (hex or Base58) for signing certificates. Unset means an ephemeral per-process key, which the API reports in every response.
ALLOW_SERVER_GRINDSet to 1 to enable the custodial grind endpoint. Off by default, on purpose.
PORTNode listen port. Default 8787.

Security model

PathWho can see the key
Browser grinderOnly your browser. No network call carries key material.
CLIOnly your machine.
Split-key delegationOnly you. The remote side holds an offset that is useless without your a1.
POST /api/grindThe server process and every hop in between. Disabled by default; treat any key it returns as compromised for anything of value.

The grind loop derives each candidate from a fresh 32-byte CSPRNG seed, incrementing only the low four bytes as a counter within a batch, so keys are unpredictable as long as the seed source is. The returned 64-byte secret key uses Solana's standard [seed][pubkey] layout and imports directly into Keypair.fromSecretKey().
